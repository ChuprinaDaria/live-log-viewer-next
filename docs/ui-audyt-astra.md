## 1. Що зараз болить

### 1.1. Каталог ролей, їх редагування і запуск читають різні джерела

Уточнення вихідної передумови: твердження про **мовчазне відкидання у `store.ts:33` не відповідає цьому checkout**. Там перевіряється ID; невідомий ID спричиняє `RoleStoreError` у `src/lib/roles/store.ts:88`. Проблема сумісності підтверджується, але механізм ширший:

| Межа | Факт із коду | Наслідок для оператора |
| --- | --- | --- |
| Тип ролі | `src/lib/roles/types.ts:1` містить рівно 8 старих ID; `src/lib/roles/types.ts:61` описує overrides лише для них | Додаткова роль не вкладається у старий контракт |
| Читання файла | `src/lib/roles/store.ts:88` кидає помилку; `src/lib/roles/store.ts:102` будує визначення через `ROLE_DEFAULTS.map` | Дозволити новий ключ у перевірці недостатньо: визначення нової ролі все одно ніде взяти |
| GET каталогу | `src/app/api/roles/route.ts:85` читає `roles_list` і `role_show`; `src/app/api/roles/route.ts:66` приводить довільний ID до старого типу | Нові ролі можуть відобразитися, хоча інші операції їх не підтримують |
| Залежність GET від старого registry | `src/app/api/roles/route.ts:88` викликає `listRoles()` навіть після успішного читання пульта; `src/lib/roles/registry.ts:131` веде до суворого store | Невалідний overrides-файл може зламати й успішне читання пульта |
| Обробка збою GET | `src/app/api/roles/route.ts:102` приховує причину й переходить до fallback; `src/app/api/roles/route.ts:110` знову викликає `listRoles()` | Fallback не гарантує відновлення, якщо помилка саме у старому store |
| Збереження | `src/app/api/roles/route.ts:131` відхиляє ID поза `ROLE_IDS` | Роль із GET може мати доступний редактор, але Save отримає 400 |
| Запуск із роллю | `src/lib/roles/registry.ts:112`, `src/lib/roles/registry.ts:139` завантажують локальні визначення | Видимість у каталозі не доводить можливості запустити цю роль |
| Інші споживачі | `src/lib/pipelines/store.ts:28`, `src/lib/mcp/server.ts:2739`, `src/lib/mcp/server.ts:2835` також фіксують ID | Виправлення лише сторінки залишить інші входи несумісними |

Додаткове обмежене читання сусіднього пульта пояснює поточний стан: `$HOME/work/fleetctl/fleetlib/roles.py:147` синхронізує overrides, перебираючи **seed**, тоді як `roles_list` перебирає весь store (`roles.py:169`). У прочитаному `$HOME/work/fleetctl/data/roles.json` було 16 ролей: 8 старих і 8 додаткових; у `roles-seed.json` — лише 8 старих. У стандартному `$HOME/.config/agent-log-viewer/state/role-presets.json` — `schemaVersion: 1` і порожній `overrides`.

Отже, у перевірених файлах додаткові ролі не були записані в overrides. Це не доказ конфігурації живого сервера: пульт допускає `LLV_STATE_DIR` (`$HOME/work/fleetctl/fleetlib/paths.py:44`), а середовище сервера не перевірялося. Команди `fleetctl roles_list/role_show` навмисно не запускалися: їхній `load()` може записати store при додаванні seed-ролей (`roles.py:102`, `roles.py:115`).

**Біль:** оператор не може трактувати «роль показана» або «збережена в пульті» як «дошка використає її при наступному запуску». Поточний опис джерела в UI обіцяє більше: `src/lib/i18n/uk.ts:2732` каже, що CLI і MCP бачать те саме.

### 1.2. Редактор ролі не дає надійно перевірити результат і зовнішні зміни

Екран уже існує: пункт «Ролі» відкривається через `src/components/mobile/MobileRootScreen.tsx:75`, сам екран — `src/components/mobile/MobileRolesScreen.tsx:27`. Є назва, engine/model/effort, позначка «змінено», опис і textarea; це добра основа, яку варто залишити (`MobileRolesScreen.tsx:99`, `MobileRolesScreen.tsx:107`). Проте:

- `src/components/mobile/rolesModel.ts:61` читає каталог при монтуванні. `refresh` повертається на рядку 84, але екран його не використовує. Редагування через пульт не підтягується у вже відкриту сторінку.
- `src/components/mobile/MobileRolesScreen.tsx:36` показує помилку завантаження лише коли ще немає списку; немає видимої кнопки повторити читання. Наявний старий список не має позначки застарілості.
- `src/components/mobile/MobileRolesScreen.tsx:82` синхронізує textarea з новою серверною копією лише при закритому рядку. Reset у відкритому редакторі оновить `role` через `rolesModel.ts:77`, але залишить старий `draft`. Старий промпт можна знову зберегти. Це висновок зі state-переходів; у браузері не відтворювалося.
- Reset доступний для будь-якої `edited` ролі (`MobileRolesScreen.tsx:127`), хоча API має опційний `seedPromptScaffold` (`src/app/api/roles/route.ts:49`). Для власної ролі без seed дія «Повернути початковий» не має очевидного змісту.
- Runtime показаний текстом (`MobileRolesScreen.tsx:102`), Save надсилає лише промпт (`MobileRolesScreen.tsx:138`). Модель та effort тут наразі не редагуються; UI має прямо пояснювати це, якщо така межа лишиться.

### 1.3. «Живий», «виконує хід», «перервано» і «завершив» змішані між поверхнями

Система вже має кілька різних доказів; додавати ще одну евристику не потрібно:

- Scanner оцінює відкритий JSONL-хід як `live` до 180 секунд тиші й `stalled` після цього; завершений хід — `recent` до 900 секунд. За відсутності розпізнаного ходу є fallback за mtime: 20/900 секунд (`src/lib/scanner/activity.ts:424`). **180 секунд тиші не доводять ані смерті процесу, ані очікування дозволу.**
- Зіставлення процесу з транскриптом окреме: записуваний fd, session ID, консервативний cwd fallback (`src/lib/scanner/transcripts.ts:28`, `src/lib/scanner/transcripts.ts:193`). Claude-subagent не отримує PID батька як власний (`src/lib/scanner/transcripts.ts:64`).
- API накладає registry-стан поверх scanner: для dead-запису без PID ставить `proc = "killed"` і terminal; для заміненого попередника також `killed` (`src/app/api/files/response.ts:426`, `src/app/api/files/response.ts:463`). Отже, `killed` тут не завжди означає аварійне переривання роботи.
- Desktop `ProcessStatusChip` показує «перервано» для `killed` або `stalled`, якщо раніше не спрацювала гілка `running` (`src/components/TaskHeader.tsx:15`). Мобільна проєкція вже розрізняє зниклий host із відкритим і завершеним ходом (`src/components/mobile/mobileBoardModel.ts:132`, `src/components/turnDuration.ts:56`). Одна завершена сесія може мати різну тривожність на різних поверхнях.
- Switchboard використовує для `stalled` фразу «перервано або чекає дозволу» (`src/hooks/useSwitchboardData.ts:56`, `src/lib/i18n/uk.ts:1857`). Слово сильніше за наявний доказ.

**Біль:** оператор домислює, чи треба відповісти агенту, просто зачекати, чи розбиратися з процесом. Перший погляд має відрізняти підтверджене питання від відсутності нових даних.

### 1.4. Транскрипт добре показує роботу, але не є перевіркою життєздатності

Шлях даних і те, що видно:

1. `$HOME/.claude/projects` є коренем scanner (`src/lib/scanner/roots.ts:68`); також враховуються зареєстровані Claude-корені (`roots.ts:79`). Проєкт визначається через cwd та recognizers (`src/lib/scanner/describe.ts:594`).
2. У проєкті відкривається розмова, її `LogFeed` підписується на хвіст (`src/components/LogFeed.tsx:345`). `useLogTail` отримує батчовані порції, тримає неповний рядок до дописування і підтримує старішу історію (`src/hooks/useLogTail.ts:223`, `useLogTail.ts:269`, `useLogTail.ts:302`).
3. Парсер з'єднує tool results із викликами, виділяє thinking і tool use (`src/components/feed/parse.ts:2663`, `parse.ts:2688`, `parse.ts:2715`). Рендер має окремі tool-картки та згортання reasoning (`src/components/feed/FeedItem.tsx:29`, `FeedItem.tsx:370`). Старі повідомлення можна довантажити; кнопка повертає до хвоста (`src/components/LogFeed.tsx:1049`, `LogFeed.tsx:907`).
4. `tickTime` рухається лише з новими байтами (`src/hooks/useLogTail.ts:285`). Але в статус передається коротке `kB · час` (`src/components/LogFeed.tsx:593`), без явного розрізнення «останній запис» і «останнє успішне читання».
5. Зелений live-tail залежить від `file.activity`, а не від успішності останнього читання (`src/components/LogFeed.tsx:894`). Таймер ходу тікає від локального годинника раз на секунду (`src/components/TurnStatusBar.tsx:17`). Сам рух таймера не є новим сигналом від агента.

Локальна вибірка: під `$HOME/.claude/projects` знайдено 760 JSONL-файлів. Прочитано лише останні до 64 KiB шести найсвіжіших; виведено агрегати типів записів, без текстів, ідентифікаторів сесій і конкретних шляхів. На момент читання два файли мали вік близько 10–14 секунд, інші — близько 5–10 хвилин. Поряд із `text`, `thinking`, `tool_use`, `tool_result` були службові `attachment`, `last-prompt`, `ai-title`, `queue-operation`; у хвостах траплялися і `tool_use`, і `end_turn` stop reasons. Це опис вибірки, не класифікація живих агентів і не повний аудит усіх 760 сесій.

**Відповідь на питання «чи достатньо транскрипту»: ні.** Він дозволяє зрозуміти останню зафіксовану дію й завершення конкретного ходу. Процес може лишатися живим після `end_turn`, довгий інструмент може мовчати, а службовий запис може освіжити файл. Потрібні окремі підтвердження host/process і свіжості спостереження. Індикація з'єднання вже є (`src/components/ConnectionPill.tsx:12`), але стосується каналу дошки; у здоровому desktop-стані вона прихована (`ConnectionPill.tsx:90`). Вона також не підтверджує життя кожного агента.

### 1.5. На компактній картці краще видно модель, ніж роль і наступну потрібну дію

У `src/components/SwitchCard.tsx:125` перший рядок містить activity dot, identity/model, effort, статус і проєкт; далі заголовок, вік, контекст, ліміти та wakeup (`SwitchCard.tsx:143`, `SwitchCard.tsx:152`). Звичайна lite-картка теж віддає перший рядок identity/status (`src/components/scheme/nodes.tsx:710`). Це вже читабельна задана анатомія; її не варто перепроєктовувати без візуальних доказів проблеми.

Водночас універсальний статус має лише `needs-you`, `held`, `running`, `queued`; для тихої картки нічого не рендериться (`src/components/cardStatus.ts:33`, `src/components/CardStatusBadge.tsx:48`). Роль у `SwitchCard` не виводиться; `RoleTag` у розглянутій lite-картці з'являється лише для flow (`src/components/scheme/nodes.tsx:741`). Метадані ролі вже можуть бути в `durableLineage.role` (`src/lib/types.ts:286`).

**Біль:** «яка модель?» видно швидше, ніж «хто цей агент у задачі?». Загальне «потребує вас» потребує відкриття розмови, щоб зрозуміти причину; у тихої картки відсутність текстового статусу не відрізняє завершений хід від невідомого стану. Не всі сесії мають роль — її відсутність слід чесно показувати, а не вгадувати з моделі або заголовка.

### 1.6. Зв'язок задачі й агента є, але в списку задач губиться результат призначення

Задача — окрема сутність зі статусами `inbox/assigned/blocked/done`; у її призначення є власні `delivered/failed/spawning/handoff`, помилка та стабільні ідентичності (`src/lib/tasks/types.ts:1`, `types.ts:5`). Панель задач показує лише кількість призначень `⤷ N` (`src/components/tasks/TaskPanel.tsx:281`). Вона не відповідає цим числом, кому доручено роботу й чи доставлено доручення.

Двосторонню навігацію вже зроблено: `TaskRelationStrip` у розмові відкриває пов'язану задачу (`src/components/tasks/TaskRelationStrip.tsx:21`, `src/components/BranchPane.tsx:442`). Але відмінність «джерело задачі» / «виконавець» там переважно в іконці та tooltip (`TaskRelationStrip.tsx:46`). **Біль:** необхідно переходити між поверхнями, щоб розрізнити створення задачі, призначення та виконання. Завершений хід агента не можна автоматично перетворювати на `task.done`.

### 1.7. «Не бачу на дошці» не означає «немає розмови»

Sidebar уже містить назву проєкту, live/attention/total і вік, підтримує закріплення та архів (`src/components/ProjectRail.tsx:75`, `ProjectRail.tsx:124`). Основний список історії має пошук, помилку з Retry і пагінацію (`src/components/ConversationList.tsx:24`, `ConversationList.tsx:49`, `ConversationList.tsx:64`). Це потрібно зберегти.

Причини неповного полотна закладені в коді: стандартне вікно scanner — 10 проєктів × 80 карток, із винятками для захищених записів (`src/lib/scanner/schemeWindow.ts:6`, `schemeWindow.ts:30`); тихі розміщені задачі згортаються у stacks (`src/components/ProjectDashboard.tsx:923`); `unplaced` задачі існують у списку без позиції на полотні (`src/lib/tasks/types.ts:74`). Пошук у `ConversationList` при непорожньому запиті стає міжпроєктним, і UI вже перемикає підказку та показ проєкту (`ConversationList.tsx:24`, `ConversationList.tsx:32`, `ConversationList.tsx:42`).

**Біль/гіпотеза для перевірки з оператором:** різні обсяги «на полотні», «у проєкті» і «в історії» потребують пояснення в місці пошуку зниклої картки. Дефекту групування або приховування живої сесії цим дослідженням не доведено; збільшувати ліміти чи міняти recognizers немає підстав.

## 2. План на завтра — за користю відносно ціни

Оцінки — людино-години одного виконавця з адресною перевіркою в ізольованих даних; без деплою й без змін живих host-процесів. Це план майбутньої реалізації, не виконані зміни. Перший пункт має найбільший ефект, попри вищу ціну: він усуває розрив між налаштуванням і виконанням.

| Порядок | Конкретна зміна | Години | Критерій готовності |
| --- | --- | --- | --- |
| 1 | Узгодити каталог ролей для читання, редагування і звичайного запуску; прибрати залежність успішного console-read від старого overrides; показувати причину деградації та доступність дій. Точки: §1.1 | 5–8 | На синтетичній додатковій ролі GET → edit → повторне читання → resolve запуску дають однакові config/prompt. Зламана одна роль не маскується старим «успішним» каталогом. Непідтримані споживачі явно відмовляють до запуску |
| 2 | Виправити слова про `stalled`, `killed` і завершений хід у desktop, узгодити з наявним mobile-розрізненням. Точки: `TaskHeader.tsx:15`, `mobileBoardModel.ts:132`, `uk.ts:1857` | 1–1,5 | Тиша не названа дозволом; штатно завершений host не позначений аварією; підтверджене питання лишається окремим приводом уваги. Перевірка також англійської локалі |
| 3 | Довести редактор: Retry/Refresh, помилка над старим списком, синхронізація textarea після Save/Reset, Reset лише з відомим seed, збереження незаписаного draft при зовнішньому оновленні. Точки: §1.2 | 1,5–2,5 | Reset у відкритому рядку одразу показує відновлений текст; зовнішня зміна не затирає draft і не видається за його успішний Save |
| 4 | Розкрити докази стану в існуючій розмові: окремо останні дані, доступність читання, підтвердження host/process, причина очікування. Точки: §1.3–1.4 | 2–3 | При помилці хвоста старий текст доступний, але UI каже «дані не оновлюються»; таймер не подається як новий heartbeat. Для недоступного доказу написано «невідомо» |
| 5 | Додати роль до компактного опису агента і текстовий підсумок призначення в панель задач, використовуючи наявні метадані та переходи. Точки: §1.5–1.6 | 1,5–2,5 | За карткою можна розрізнити роль і модель; за задачею — виконавця та недоставлене призначення. Без нової сутності «агент» і без автоматичного `done` |
| 6 | Уточнити підказки обсягу полотна/історії та перехід до повного списку, якщо Даша підтвердить проблему. Точки: §1.7 | 0,5–1 | Згорнуту або нерозміщену задачу знаходять через наявний список; порожній результат не пояснюється «нічого не працює» |

**Реалістична межа завтра — 8 годин:** брати пункти 1 і 2, якщо пункт 1 вклався у 6–6,5 години; решту залишити впорядкованим резервом. Якщо каталог потребує всіх 8 годин, не обіцяти ще й нові картки. Перший завершуваний крок пункту 1 — чесні стани помилки/несумісності (приблизно 1 година всередині оцінки), потім спільне читання й resolve. Повний перелік становить 11,5–18 годин, а не один робочий день.

Наскрізна міграція dynamic-role контрактів pipeline/MCP і політик дозволів може додати ще 2–4 години до пункту 1. Не приховувати цю залежність: перед початком вибрати підтримувані входи, а непідтримані чітко позначити. Роль не можна назвати «готовою до запуску всюди», доки старі enum-перевірки там лишаються. Особливо не перетворювати відмову reviewer/verifier у право на spawn лише через новий ID: поточні обмеження теж прив'язані до назв (`src/lib/agent/spawnAdmission.ts:9`).

### Як має виглядати сторінка ролей після виправлення

Залишити поточний список із розгортанням рядка. Каталог відображає всі визначені пультом ролі, а не фіксовані вісім. Для прочитаних даних це 16; рішення про приховування старих восьми належить оператору, а не міграції UI.

| Стан | Текст і доступні дії |
| --- | --- |
| Каталог успішно прочитано | «Ролі з пульта · 16 · оновлено …», кнопка «Оновити». У рядку: назва, коротке призначення, engine/model/effort, стан зміни |
| Роль валідна для обраного способу запуску | «Доступна для нового запуску». Якщо pipeline ще не підтримується, це явно зазначено окремо |
| Власна роль без seed | «Власна роль»; редагування доступне, дії «Повернути початковий» немає |
| Роль прочитана, але конфігурація не приймається споживачем | Рядок лишається видимим: «Не можна запустити: …». Показати конкретне поле/обмеження; не підміняти роль старою моделлю |
| Пульт недоступний, є остання успішна копія | «Не вдалося оновити · показано дані станом на …», Retry; жодного удаваного підтвердження запису |
| Доступний лише вбудований каталог | «Вбудовані ролі · дані пульта недоступні». Окремо вказати причину: відсутній пульт, збій читання або несумісність. Read-only, як уже задумано |
| Збереження успішне | Показати підтверджену повторним читанням конфігурацію; textarea відповідає їй. «Збережено для наступних запусків» |
| Запис успішний, перевірка читання не вдалася | «Зміни записано, актуальну версію не підтверджено» + повторити читання; не рекомендувати повторний запис навмання |
| Пульт змінив роль, поки є локальний draft | «Є новіша версія в пульті»; дати переглянути її та зберегти власний текст без мовчазної втрати |

У розгорнутому рядку: опис, промпт, зрозуміла межа редагованих полів, час підтвердженої зміни, Save і за наявності seed — Reset. Промпт та runtime — різні поля; якщо runtime редагується лише в пульті, написати це поруч із його значенням. Дані про grants API вже повертає (`src/app/api/roles/route.ts:78`); їх редагування не включати в завтрашній мінімум. Зміна preset не повинна обіцяти переналаштування вже живих агентів: показувати конфігурацію наступного запуску окремо від фактичної конфігурації поточної розмови.

### Мінімальний контракт стану розмови

На картці — коротке слово і причина, у розкритті — джерело та час доказу. Не додавати всі технічні поля в кожну картку.

| Наявний доказ | Що написати |
| --- | --- |
| Є pending question/plan | «Потрібна відповідь» / «Потрібне затвердження плану», перехід до самого питання |
| Є відкритий хід і підтверджений доступний host | «Виконує хід · …»; останній запис — окремий час |
| Хід відкритий, нових записів давно немає | «Немає нових даних · …»; host «підтверджено» або «невідомо» за фактичним доказом |
| Хід завершився, host лишився доступним | «Хід завершено · можна продовжити»; це не статус готовності задачі |
| Host завершився після закритого ходу | «Сесію завершено» у нейтральному тоні |
| Host зник із підтверджено відкритим ходом | «Зв'язок з агентом втрачено під час виконання»; відкрити деталі, без автоматичного рестарту |
| Читання недоступне чи доказів недостатньо | «Стан невідомий · останні дані …»; не зелений висновок із самого таймера |

Адресна перевірка майбутньої реалізації: fixtures ролей із додатковим ID, відсутнім seed, зіпсованим overrides та збоєм повторного читання; UI-переходи Save/Reset; стани quiet-live-host, completed-stopped-host, open-turn-host-gone, tail-error. Використовувати конкретні відповідні test-файли й приватний state directory. У межах цього дослідження нічого з цього не запускалося.

## 3. Чого НЕ робити

- **Не перезапускати дошку або runtime host, не пробувати запуск/kill/resume живої сесії задля UI-перевірки.** Це прямо заборонено умовою; статичного аналізу достатньо для плану.
- **Не замінювати старі вісім `ROLE_IDS` новими вісьмома і не прибирати перевірки одним `as string`.** `mergeRoleDefinitions` усе одно перебирає defaults (`src/lib/roles/store.ts:102`), а запуск і політики мають свої залежності. Потрібен узгоджений каталог і чесна доступність операцій.
- **Не маскувати збій пульта завжди успішним fallback.** Причина повинна бути видима; інакше оператор знову отримає старі значення після «успіху» (`src/app/api/roles/route.ts:102`).
- **Не вводити другий heartbeat або таймер «живий» від mtime.** Уже є process/registry/turn/transport; пояснити їх наявні докази дешевше й точніше (`src/lib/scanner/activity.ts:424`, `src/app/api/files/response.ts:426`).
- **Не редизайнити canvas, sidebar, кольорову систему, drag-and-drop чи навігацію цілком.** Картки вже мають задану анатомію, а історія — пагінацію й Retry (`src/components/scheme/nodes.tsx:707`, `src/components/ConversationList.tsx:49`). Проблеми переповнення або контрасту без браузера тут не встановлені.
- **Не збільшувати ліміти scanner і не монтувати всі 760 транскриптів одночасно.** Вікно має окремий захист живих записів (`src/lib/scanner/schemeWindow.ts:30`), а lite-картки навмисно не відкривають повні транскрипти (`src/components/scheme/nodes.tsx:680`).
- **Не міняти project grouping або створювати проєкт на кожен worktree.** Наявний `projectInfoFromCwd` — канонічний шлях; UI-скарга на пошук розмови не доводить дефект recognizer (`src/lib/scanner/describe.ts:594`).
- **Не робити автоматичні висновки «агент завершив хід → задача готова» або «роль має певну модель → це reviewer».** Стан задачі та зафіксована роль мають власні дані (`src/lib/tasks/types.ts:1`, `src/lib/types.ts:286`).
- **Не запускати broad test suites проти живого registry; не переносити тексти локальних розмов, персональні шляхи чи ідентичності у fixtures.** Для завтрашніх перевірок достатньо синтетичних сценаріїв.

## 4. Відкриті питання до Даші

1. Нові вісім ролей мають замінити старі в основному списку чи співіснувати з ними? Зараз у store є обидві групи; автоматично видаляти або приховувати старі немає підстав.
2. Який вхід має запрацювати першим: редагування в «Ролях», звичайний запуск із preset чи запуск через pipeline/MCP? Це визначає, чи вкладається критичний шлях у день.
3. Де саме спостерігалося «успішно збережено, але дошка не бачить»: у пульті, у сторінці ролей чи у виборі ролі перед запуском? У поточному коді ці три шляхи мають різні відмови. Чи стосується випадок цього checkout або раніше розгорнутої версії?
4. Коли питаєш «агент живий», що найчастіше потрібно вирішити: чи він ще виконує завдання, чи можна йому написати, чи процес узагалі існує? Пропозиція за замовчуванням — стан ходу на картці, host і останні дані у розкритті.
5. Чи достатньо першого погляду «роль · стан · поточний крок», залишивши model/effort другим рівнем? Чи модель є основним способом вибрати агента саме у твоєму щоденному сценарії?
6. Чи потрібно завтра редагувати model/effort зі сторінки ролей, чи досить промпту та точного показу runtime, зміненого в пульті? Це окрема робота, якої поточний textarea не виконує.
7. Чи регулярно губляться нерозміщені/згорнуті задачі або розмови між проєктом і загальним пошуком? Якщо ні, пункт про scope-підказки залишити резервом; не витрачати на нього перший день.
